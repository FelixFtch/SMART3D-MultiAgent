What I Built, What I Borrowed, and What Failed Along the Way

A plain-language explanation of SMART-3D multi-agent navigation research — from the original paper to my extensions.

Part 1: What did the original SMART-3D paper give us?

SMART-3D is a path planning algorithm published by Zongyuan Shen at UConn. The core idea: instead of throwing away your entire plan every time something changes, fix only the broken parts.

The Tree Metaphor

Imagine a robot needs to navigate from point A to point B. RRT* (the underlying planner) works by growing a "tree" of possible paths — thousands of branches spreading out from the start, exploring the space randomly. One of those branches eventually reaches the goal. That's your path.

The tree has ~15,000 nodes connected by edges. Building it takes ~40ms on an i9 processor. Not bad for a one-time cost. But what happens when a person walks into the robot's way?

What the original paper does

SMART's key insight: When an obstacle appears, don't rebuild the whole tree. Instead: (1) identify which edges the obstacle blocks, (2) cut those edges, (3) reconnect the broken pieces using nearby nodes that still have valid connections. This takes ~5ms instead of ~40ms.

The paper handles dynamic obstacles (people walking around) with this technique. It uses an "OHZ" (Obstacle Hazard Zone) — a bubble around each person that accounts for their speed and direction. Edges entering the OHZ get cut, then reconnected when the person moves away.

What the paper does NOT handle

The paper assumes the robot already knows the entire map — every wall, every corridor. In real life, a robot entering a building for the first time has no map. It discovers walls one by one through its LiDAR sensor. The paper's algorithm never needed to deal with "new permanent walls appearing."

This is the gap I filled.

Part 2: What happens when a robot enters an unknown building?

Walkthrough: Robot enters mega_hospital (64×64m, ~200 walls)

1
Robot starts at corner (2,2). LiDAR scans 12m radius. Discovers 15 nearby walls. Builds an RRT* tree with 30,000 nodes using those 15 walls. Finds a path to goal at (62,62). Path goes straight through the middle — but there are walls there it doesn't know about yet.
2
Robot starts following the path. After 20 seconds, it moves far enough to discover 3 new walls directly ahead. Its path goes right through one of them. What now?
3
This is where my work begins. The original paper has no mechanism for this because it assumed all walls were known from the start. I need to update the tree to account for new permanent walls — and I need to do it fast, because the robot is still moving.

Part 3: Five approaches I tried (and what happened)

Approach 1: Full Rebuild — The Brute Force Baseline

!
New wall discovered → Throw away the entire 15,000-node tree. Build a completely new one from scratch, now including the new wall. Takes ~40ms each time. Robot freezes while tree rebuilds.

Sounds reasonable? Here's the problem: in mega_hospital, the robot discovers ~200 walls over the course of a run. Each discovery triggers a full rebuild. That's 200 × 40ms = 8 seconds of freeze time, plus the tree quality degrades because each new tree is random — it might be worse than the old one.

Approach 2: Eager Incremental — My Core Innovation

Instead of throwing away the tree, I reuse the original paper's repair mechanism — but apply it to permanent walls instead of moving people.

1
New wall discovered. Scan every edge in the tree (15,000 of them). Check: does this edge cross the new wall? Most don't. Typically ~20 edges do.
2
Cut the ~20 bad edges. This splits the tree into a main tree and a few disconnected "subtrees" — islands of nodes that lost their connection to the root.
3
Reconnect. For each disconnected subtree, search for nearby nodes in the main tree. If there's a valid edge between them (one that doesn't cross any wall), reconnect. The paper calls these "hot nodes."
4
Update costs. Reconnected nodes may have different path costs now. Propagate the new costs down the tree. Build a new path to goal using the repaired tree.
Why this works so well

99% of the tree is unaffected by any single new wall. I keep all of it. Only the ~20 broken edges need repair. The tree's overall quality is preserved — no random rebuilding, no quality loss.

MetricFull RebuildEager Incremental
Megacampus median76.3s8.71s (8.8x faster)
Rebuilds per run139.62.2
Success rate96.6%99.9%
Complexity per wallO(K log K)O(N × W) scan + O(h) reconnect

N = 15,000 nodes, W = all known walls (~300 at end), h = hot nodes (~50). The scan is the expensive part: 15,000 × 300 = 4.5 million edge-wall intersection tests. But each test is just a Liang-Barsky line-rectangle check (~5 nanoseconds), so total is ~22ms. Much cheaper than a full 40ms rebuild.

Approach 3: Lazy Swap — Trading Reliability for Speed

I noticed something: most new walls don't actually block the robot's current path. The robot is heading east, and the wall it discovered is in the north corridor. Why spend 22ms scanning the whole tree if the path is fine?

1
New wall discovered. Quick check: does my current path cross this wall? No.
2
Just swap the collision checker. Don't scan the tree, don't cut any edges. Simply update the "rule book" so that future path planning knows about the wall. Cost: ~0ms.
3
But this leaves "dirty edges" in the tree — edges that cross the new wall but haven't been cut. If the robot later needs to replan (because a person blocked the path), it might use one of those dirty edges and plan a path through a wall.

Megacampus median8.71s3.40s (22.4x vs Full)
Success rate99.9%97.4% (dirty edges cause failures)

Approach 4: Hybrid — The Middle Ground That Didn't Work

I tried a compromise: when the path isn't affected, do a light edge cleanup — only check edges against the new wall (not all walls), and do a quick reconnect. This should catch dirty edges without the full scan cost.

Result: Abandoned

Hybrid achieved 3.42s median (same as Lazy) with 98.6% success (better than Lazy but worse than Eager). It was strictly dominated: no faster than Lazy, no more reliable than Eager. The extra code complexity wasn't worth the marginal improvement.

Approach 5: Lazy + Eager Combo — The Final Architecture

The key insight: I don.t need to choose between Lazy and Eager. I can use both, depending on the situation.

The Decision Rule

?
New wall discovered. Does my current path cross any known wall?
A
Path is clear → Lazy Swap. Just update the checker, move on. ~0ms. Yes, dirty edges accumulate, but the path is safe right now.
B
Path is blocked → Eager Repair. Full tree scan, cut all bad edges, reconnect everything. ~22ms. Cleans up ALL dirty edges from previous lazy swaps too, because the checker now contains all known walls.
Why this is better than either alone

Most wall discoveries don't block the path → handled by Lazy at ~0ms cost. When the path IS blocked (less common), Eager kicks in and cleans the entire tree. The dirty edges from Lazy never survive long — the next path-blocking wall triggers a full cleanup.

In mega_hospital, about 80% of wall discoveries are handled by Lazy, 20% by Eager. Total repair cost drops dramatically while maintaining high reliability.

Full Rebuild 76.3s → Eager 8.71s → Lazy 3.40s → Hybrid 3.42s ✗ → Lazy+Eager ★

Part 4: The Extras — Detour Detection and Path Shortcutting

Shortcut (marginal benefit)

After building or repairing a path, randomly pick two points on the path and check: can you draw a straight line between them without hitting any wall? If yes, replace the curved segment with the straight line. Repeat 150 times. This shaves off ~3-5% of path length.

Detour Detection (useful but not critical)

After several incremental repairs, the path might become 1.5x longer than optimal (the tree accumulated so many patches that the path zigzags). Detour detection notices this and triggers a full rebuild to get a clean path. This helps ~10-15% on mega maps.

Multi-agent result: both are nearly useless

In 4-agent scenarios, shortcut and detour provide less than 1% improvement. The reason: coordination overhead (agents waiting for each other) dominates path quality. A 5% shorter path doesn't help when you spend 10 seconds waiting for the king agent to clear the corridor.

ConfigMegacampus 4-agent
E3 (shortcut + detour)95.6s
No shortcut95.5s
No detour94.5s
Baseline (neither)93.7s

Baseline is actually fastest because it doesn't waste CPU cycles on shortcutting. I kept them in the final system because they help in single-agent scenarios, but they're not a contribution.

Part 5: LSR — The Parameter That Actually Mattered

LSR stands for "Local Search Region" — the radius within which SMART searches for hot nodes to reconnect broken subtrees. The original paper used LSR = 10m (designed for small lab environments).

My maps are 64–128m. When a wall breaks an edge, the nearest reconnection point might be 30m away (around a long corridor). LSR = 10m can't reach it → repair fails → fall back to full rebuild.

Discovery: LSR = 80m is the sweet spot

I swept LSR from 10 to 120m. Repair success rate jumped from ~70% (LSR=10) to ~92% (LSR=80). Beyond 80m, diminishing returns — the search region is so large it includes too many irrelevant nodes.

This is arguably the single most impactful parameter change. It's why my incremental repair succeeds 92% of the time (vs Senior's 33% path-only repair success rate). Not a code change — just understanding that the paper's default was tuned for small environments.

Part 6: Engineering or Innovation?

Honest assessment of each piece:

ContributionTypeWhy
update_static_obstacles() Novel extension The paper's update() handles dynamic obstacles. I extended the same prune-reconnect framework to permanent walls in unknown environments. Same mechanism, fundamentally different problem: dynamic obstacles disappear, walls don't. This requires different tree management (form_single_tree_after_static_update vs the original's form_single_tree).
Lazy + Eager combo Novel architecture The decision to skip tree scanning when path is unaffected, combined with full repair when path is blocked, doesn't exist in the paper or any SMART variant. It's an engineering-informed design choice validated by 1000-trial benchmarks.
LiDAR wall discovery System integration Simulated ray-casting against ground truth walls, fog-of-war grid, wall occlusion. Standard robotics technique but necessary to create the unknown-environment problem.
Multi-agent coordination Novel system Global King priority, flee, chain push, shared wall discovery — none of this exists in SMART-3D. The paper is single-robot only. My reactive coordination in continuous space is a new approach to multi-robot navigation with sampling-based planners.
Shared wall discovery Novel mechanism Agent A's LiDAR discovers a wall → Agent B's tree is updated. This creates an information-sharing network that speeds up navigation by 1.04x–2.09x. No prior work combines incremental tree repair with cooperative map sharing.
LSR = 80m Parameter tuning Important for practical performance but not a conceptual contribution. The insight that large maps need large search regions is straightforward.
Shortcut / Detour Standard technique Path shortcutting is textbook. Detour detection is a simple heuristic. Neither contributes meaningfully in multi-agent scenarios.
Spatial Index v2 Engineering optimization Grid-bucket for is_edge_valid(). Standard spatial data structure, applied to reduce wall-clock time. −26% on mega maps.
Summary: What's actually new

Three genuinely novel pieces: (1) incremental tree repair for permanent walls in unknown environments, (2) the Lazy+Eager adaptive architecture, and (3) multi-agent coordination with shared wall discovery using sampling-based planners.

Everything else is either parameter tuning (LSR), standard technique (shortcut), system integration (LiDAR), or engineering optimization (spatial index). Still necessary for the system to work, but not paper-worthy on their own.

Part 7: Exactly What I Borrowed from SMART-3D

The SMART crate provides these APIs that I use directly, without modification:

APIWhat it doesHow I use it
SMART::update() Prune edges inside OHZ (Obstacle Hazard Zone), find hot nodes, reconnect broken subtrees Called every frame for dynamic obstacle (people + other agents) avoidance. This is the original paper's main contribution and I don.t change it.
RRTstar::new() Build initial tree with K iterations Called once per agent at startup, and again on full rebuild. I added 8% goal-bias sampling but the core algorithm is unchanged.
build_planned_path() Find path from robot to goal by backtracking through parent pointers Called after every repair to get the updated path. Unmodified.
hot_node_search() Find nodes that can bridge two disconnected subtrees Used inside my update_static_obstacles(). The search logic is from the paper; I just call it in a new context (static walls instead of dynamic obstacles).
KdTreeNearestNeighbors Spatial lookup of nearby nodes Used for hot-node search and tree growth. Unmodified.
The honest framing

"I build upon SMART-3D's incremental repair framework and extend it to unknown environments with multiple agents. The core prune-reconnect mechanism is from the original paper. My contributions are the static-wall repair pipeline, the Lazy+Eager adaptive architecture, and the multi-agent coordination system with cooperative map sharing."
